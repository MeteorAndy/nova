# Mobile Workbench v2: replace the legacy mobile layout

> Status: ready for implementation after publication
>
> Issue target: `MeteorAndy/nova`

## Problem Statement

Denova 当前的移动端是从桌面多面板工作台压缩而来：一级入口过多，项目与 Agent 依赖抽屉和隐藏边缘手势，编辑器、Agent Dock、工具栏和底栏争夺有限的屏幕空间。用户虽然能找到部分桌面能力，但很难在手机上保持方向感、专注完成任务或可靠恢复工作现场。

问题不仅是视觉拥挤。当前移动呈现还把“书籍”“workspace”和创作项目边界混在一起；共享菜单可能影响模式状态；Agent 运行、变更审阅、故事回合、状态编辑和后台任务缺少一致的移动恢复路径；单一 `767px` 开关也无法合理覆盖大屏手机、横屏和平板。继续在旧外壳上增加入口或抽屉会扩大条件分支，并使写作与游戏形成两套不一致的产品行为。

移动创作者需要一个能力完整但认知负担更低的工作台：任何时刻只处理一个主要任务，所有重要状态可恢复，写作与游戏使用同一套产品规则，并能在手机、平板和桌面之间安全继续创作。

## Solution

用 Mobile Workbench v2 直接替换旧移动布局。新工作台采用稳定的单主工作面应用外壳：顶部栏定位当前工作对象，底部固定四个带文字的一级入口，中间区域只承载当前任务。写作模式使用“正文、项目、Agent、更多”，游戏模式使用“故事、剧情线、资料、更多”。模式只能由用户在“更多”顶部明确切换，并分别保存自己的工作状态；任何共享功能都不能自动切换模式。

正文、Agent、故事舞台和复杂管理功能分别使用适合手机的完整工作面，不再复制桌面分栏。Agent 运行和其他长时间操作统一成为可恢复后台任务；上下文只能通过用户可检查的明确交接进入 Agent；文件变更进入独立全屏审阅；故事回合使用提交时上下文快照，历史修改通过修订或创建分支完成；当前状态和世界资料保持清晰的数据边界。

布局按可用容器空间分为手机、紧凑宽屏/平板和桌面三层。业务行为、保存契约、任务生命周期、项目隔离和审计规则跨设备一致，只有呈现方式自适应。移动 PWA 保护短时断线草稿，但不宣称完整离线工作区。

## User Stories

1. 作为移动创作者，我希望任意时刻只看到一个主要工作面，从而能专注完成当前任务。
2. 作为移动创作者，我希望所有一级入口都有图标和文字，从而不必猜测图标含义。
3. 作为移动创作者，我希望任意时刻只有一个一级入口高亮，从而始终知道自己在哪里。
4. 作为移动创作者，我希望写作模式只有“正文、项目、Agent、更多”四个一级入口，从而快速进入最高频流程。
5. 作为游戏创作者，我希望游戏模式只有“故事、剧情线、资料、更多”四个一级入口，从而快速进入最高频流程。
6. 作为跨模式创作者，我希望只能在“更多”中明确切换写作或游戏模式，从而避免误触菜单改变工作上下文。
7. 作为跨模式创作者，我希望写作与游戏分别记住上次入口、对象、滚动位置和输入草稿，从而切换后能继续原任务。
8. 作为跨模式创作者，我希望打开版本、Skills、Agents、自动化或设置时不改变当前模式，从而保持稳定的创作上下文。
9. 作为移动创作者，我希望项目切换和模式切换是两个独立动作，从而不会因为打开另一项目而进入错误模式。
10. 作为移动创作者，我希望项目切换前可靠保存当前可保存内容，从而不会因切换丢失编辑。
11. 作为移动创作者，我希望保存失败时留在当前项目并看到具体错误，从而能够处理问题而不是进入不确定状态。
12. 作为移动创作者，我希望顶部栏以当前章节、会话、故事或资料条目为主标题，从而快速确认当前工作对象。
13. 作为移动创作者，我希望顶部栏以当前创作项目为副标题并可进入项目切换，从而无需占用额外全局导航空间。
14. 作为移动创作者，我希望长标题不会遮挡返回和操作按钮，从而在中英文和小屏幕上都能正常操作。
15. 作为移动创作者，我希望顶部栏只保留最多两个高频操作，从而避免把桌面工具条压进手机。
16. 作为写作者，我希望手机正文一次只显示一个文档，从而获得足够的阅读和编辑宽度。
17. 作为写作者，我希望点击正文标题即可查看最近打开文档，从而快速切换而不需要可见 Tab 栏。
18. 作为写作者，我希望每个已打开文档分别保留草稿、光标、选区、滚动和撤销历史，从而切换文档后能原位继续。
19. 作为写作者，我希望在标题附近看到保存中、已保存、离线或冲突状态，从而明确内容是否安全。
20. 作为写作者，我希望“项目”默认显示按卷、章节和规划文档组织的大纲，从而按照创作结构而不是磁盘目录工作。
21. 作为高级用户，我希望“项目”仍提供完整文件分段，从而能够管理非正文文件和原始目录。
22. 作为写作者，我希望搜索同时覆盖正文、规划文档和资料，从而不必在多个页面分别搜索。
23. 作为写作者，我希望点击章节后自动进入正文并恢复该文档状态，从而连续编辑。
24. 作为写作者，我希望返回项目时恢复原分段、展开节点、筛选和滚动位置，从而继续原来的整理任务。
25. 作为移动创作者，我希望普通项目浏览不会启用拖拽，从而避免滚动时误改结构。
26. 作为移动创作者，我希望只有明确进入排序状态才出现拖拽手柄，从而让结构调整可预期。
27. 作为写作者，我希望键盘打开时一级导航隐藏并显示正文编辑工具栏，从而让输入控件完整占用底部空间。
28. 作为写作者，我希望普通编辑工具栏只包含撤销、重做、段落、粗体、斜体、插入和收起键盘，从而保持稳定且易触达。
29. 作为写作者，我希望存在选区时原工具栏切换为格式、评论、询问 Agent 和更多动作，从而不叠加第二排控件。
30. 作为写作者，我希望选区 AI 能力来自明确的 Agent 交接或适用 Skills，从而避免隐式注入内容。
31. 作为 Agent 用户，我希望移动端一次只显示一个完整 Agent 会话，从而有足够空间阅读消息和工具结果。
32. 作为 Agent 用户，我希望点击会话标题进入可搜索的全屏会话管理，从而切换、重命名、新建或删除会话。
33. 作为 Agent 用户，我希望每个会话保留输入草稿、滚动位置和运行状态，从而切换会话后能继续。
34. 作为 Agent 用户，我希望工具调用、子 Agent 和诊断信息以可展开卡片出现在消息流中，从而按需查看而不占固定侧栏。
35. 作为写作者，我希望普通切换到 Agent 时不会自动附加当前文档或选区，从而避免无意泄露或浪费上下文。
36. 作为写作者，我希望通过“询问 Agent”或“讨论本章”显式交接内容，从而准确控制 Agent 获得的信息。
37. 作为 Agent 用户，我希望发送前看到每个交接片段的来源、用途、版本和大小并可以移除，从而检查最终模型输入。
38. 作为 Agent 用户，我希望所有交接内容遵守可配置的高上下文上限，从而避免无限历史或文件内容进入提示词。
39. 作为 Agent 用户，我希望离开 Agent 工作面后运行继续，从而可以同时编辑正文或管理项目。
40. 作为 Agent 用户，我希望返回会话时从持久状态恢复消息、工具结果和进度，从而不依赖原流式连接仍然存在。
41. 作为 Agent 用户，我希望只有明确停止才终止运行，从而不被路由变化或写死超时中断。
42. 作为移动创作者，我希望 Agent 文件变更只先显示摘要，从而不会自动打断当前工作面。
43. 作为移动创作者，我希望点击摘要后进入独立全屏单栏 Diff，从而清晰检查每个文件的修改。
44. 作为移动创作者，我希望能够在 Diff 中留下有来源且大小有界的反馈，从而把具体意见交回 Agent。
45. 作为移动创作者，我希望从变更审阅接受、撤销或继续修改，从而在一个明确流程中完成决策。
46. 作为移动创作者，我希望审阅完成后回到原 Agent 会话，从而保持任务连续性。
47. 作为跨项目用户，我希望每个 Agent 运行严格绑定来源项目和会话，从而不会污染当前项目。
48. 作为跨项目用户，我希望运行中的 Agent 不阻止我切换项目，从而可以并行推进多个创作项目。
49. 作为跨项目用户，我希望打开其他项目的运行前先保存当前现场并恢复到正确来源，从而安全处理跨项目任务。
50. 作为移动创作者，我希望 Agent、自动化、图像生成和批量导入导出统一进入任务中心，从而在一个地方发现长时间任务。
51. 作为移动创作者，我希望任务显示来源项目、类型、状态、开始时间和恢复目标，从而知道发生了什么以及如何继续。
52. 作为移动创作者，我希望只有等待用户和失败任务计入数字徽标，从而避免运行中任务持续制造焦虑。
53. 作为移动创作者，我希望任务完成或失败不会自动抢回前台，从而不打断当前创作。
54. 作为移动创作者，我希望应用内任务中心始终可用，从而不依赖系统通知发现关键状态。
55. 作为重视隐私的用户，我希望系统通知默认关闭且首次启动不请求权限，从而自主决定是否启用。
56. 作为启用通知的用户，我希望通知只显示任务类型和来源项目而不包含敏感正文，从而兼顾可行动性与隐私。
57. 作为游戏创作者，我希望“故事”默认进入故事舞台而不是导演配置，从而直接试玩玩家体验。
58. 作为故事玩家，我希望 AI 叙事使用全宽阅读排版而不是聊天气泡，从而获得连贯的故事阅读体验。
59. 作为故事玩家，我希望角色对白显示说话者和可用头像或立绘，从而清晰理解场景参与者。
60. 作为故事玩家，我希望玩家行动显示为紧凑、可辨识的行动块，从而与叙事结果区分。
61. 作为故事玩家，我希望检定、状态变化和工具过程收纳为可展开事件卡，从而按需检查细节。
62. 作为故事玩家，我希望场景图像存在时清晰展示并支持全屏查看，从而检查真实内容而不是装饰背景。
63. 作为故事玩家，我希望没有场景图像时仍有完整纯文本体验，从而不被无意义占位打断。
64. 作为故事玩家，我希望最多三项行动建议直接显示且其余进入更多选择，从而兼顾选择速度和屏幕空间。
65. 作为故事玩家，我希望点击行动建议只填入自由输入框，从而能够修改后再明确发送。
66. 作为故事玩家，我希望流式生成期间保留输入草稿但禁止重复提交，从而避免创建重复回合。
67. 作为游戏创作者，我希望从故事顶部明确进入独立导演台并返回原故事位置，从而分离试玩与导演工作。
68. 作为游戏创作者，我希望玩家发送行动时锁定回合上下文快照，从而让一次生成使用一致的输入版本。
69. 作为游戏创作者，我希望生成期间保存的新导演规则从下一回合生效，从而不会在同一回合混合新旧配置。
70. 作为游戏创作者，我希望需要新配置影响当前回合时必须明确停止并重新生成，从而保留可审计的执行边界。
71. 作为游戏创作者，我希望修改没有后续依赖的最新回合时产生回合修订记录，从而保留更正历史。
72. 作为游戏创作者，我希望修改存在后续依赖的历史回合时必须创建新分支，从而不破坏原故事路径。
73. 作为游戏创作者，我希望原分支在创建新分支后完整保留，从而可以随时恢复或比较旧路径。
74. 作为游戏创作者，我希望手机剧情线默认显示当前分支置顶的纵向列表，从而无需在二维画布中寻找当前位置。
75. 作为游戏创作者，我希望分支项显示分歧回合、父分支、摘要、回合数和更新时间，从而快速判断路径差异。
76. 作为游戏创作者，我希望进入分支详情后通过纵向时间线切换、重命名、继续或删除，从而完成日常分支管理。
77. 作为游戏创作者，我希望关系图是次级总览并在宽屏增强，从而手机日常流程不依赖平移、缩放或小地图。
78. 作为游戏创作者，我希望“资料”明确分为当前状态和世界资料，从而不混淆分支运行状态与项目稳定设定。
79. 作为游戏创作者，我希望当前状态默认展示当前分支并保持只读，从而快速检查而不误改未来剧情输入。
80. 作为游戏创作者，我希望修改当前状态必须进入全屏状态修订并检查变化摘要，从而留下来源、时间、分支和基准回合记录。
81. 作为游戏创作者，我希望状态修订只影响目标分支且支持撤销或恢复，从而不反向改写世界资料。
82. 作为内容维护者，我希望设置、Skills、Agents、自动化和版本在手机上使用列表到全屏详情，从而避免压缩桌面表格和多栏。
83. 作为内容维护者，我希望返回管理列表时恢复搜索、筛选、滚动和选中项，从而继续原管理任务。
84. 作为配置维护者，我希望可执行配置先成为本地草稿并在完整校验后明确保存，从而避免半成品改变运行行为。
85. 作为配置维护者，我希望带未保存配置返回时选择继续编辑或放弃，从而不静默生效或丢失草稿。
86. 作为内容创作者，我希望正文和世界资料持续自动保存草稿并显示冲突，从而减少移动输入丢失风险。
87. 作为普通用户，我希望语言、主题、字体和动效等即时偏好自动保存并立即生效，从而减少不必要确认。
88. 作为移动 PWA 用户，我希望短时断线时仍能编辑已经打开的正文和输入草稿，从而应对网络波动或系统挂起。
89. 作为移动 PWA 用户，我希望断线修改绑定创作项目和基础版本持久保存，从而重连时可以安全校验。
90. 作为移动 PWA 用户，我希望远端变化时进入冲突审阅而不是直接覆盖，从而保护多设备内容。
91. 作为移动 PWA 用户，我希望断线时不能提交运行、切换项目或执行结构迁移，从而避免伪离线产生不可解释状态。
92. 作为手机用户，我希望顶部返回、Android 返回和浏览器返回使用同一导航栈，从而每次返回结果都可预测。
93. 作为手机用户，我希望一次返回依次处理键盘、表层、未保存保护和全屏子工作面，从而不会跳过关键状态。
94. 作为手机用户，我希望产品不占用左右边缘手势，从而保留系统返回、浏览器导航和文本选择。
95. 作为平板用户，我希望空间足够时列表和详情可以双栏显示，从而利用更大屏幕而不改变任务语义。
96. 作为桌面用户，我希望继续使用可调整多栏和可见文档 Tab，从而保持高密度工作效率。
97. 作为跨设备用户，我希望旋转屏幕或跨越布局层级时编辑器和会话不被重建，从而保留草稿、滚动、选区和撤销历史。
98. 作为触屏宽屏用户，我希望粗指针设备仍保持足够大的触控目标，从而不因宽度增加而变得难以操作。
99. 作为中文用户，我希望所有用户可见文案、状态、错误和空状态都有完整中文，从而可以独立完成所有流程。
100. 作为英文用户，我希望所有界面在真实长英文下无截断和遮挡，从而获得与中文一致的能力。
101. 作为使用屏幕阅读器的用户，我希望导航、工作区、对话框和动态任务状态具有正确语义，从而理解当前位置和变化。
102. 作为键盘用户，我希望所有核心流程可通过正常焦点顺序完成，从而不依赖触屏或隐藏手势。
103. 作为低视力用户，我希望 200% 字体缩放下内容和操作仍可达，从而不因小屏布局失去功能。
104. 作为减少动态效果的用户，我希望系统遵守减少动效偏好且流式内容保持稳定，从而避免持续跳动造成不适。

## Implementation Decisions

- “创作项目”是顶层用户内容边界，拥有写作内容、互动故事、资料、Agent 会话、配置和版本历史；“书籍”只表示写作成果身份。现有 Book、workspace 和书籍命名必须通过有备份且可回滚的迁移逐步统一。
- 写作与游戏的业务行为跨设备统一。四入口、单主工作面、隐藏移动 Tab、全屏详情和列表优先剧情线只属于移动呈现。
- 手机层采用固定四入口，紧凑宽屏在保持同一导航语义的前提下可转为窄侧栏，桌面恢复活动栏。初始容器参考范围为小于 640px、640px 至 1099px、1100px 及以上；组件只有满足自身最小内容宽度时才能升级布局。
- 一级入口切换不持续压入历史；顶部返回、Android 返回和浏览器历史共享一个逻辑栈。返回优先处理键盘、最上层表层、未保存配置、全屏子工作面和“更多”子功能。
- 模式切换只能由用户在“更多”顶部的分段控件触发。共享能力、项目切换和返回行为不得隐式切换模式。
- 写作和游戏分别持久化模式工作状态。每个文档、Agent 会话、故事分支和管理列表也分别保存自己的可恢复状态。
- 响应式变化通过稳定内容宿主移动现有内容，不通过卸载和重建编辑器、会话或故事舞台实现。
- 移动顶部栏使用工作对象主标题与创作项目副标题。右侧最多两个高频操作，其余进入成熟菜单组件；品牌、通知、全局搜索和模式开关不常驻。
- 移动正文使用单文档呈现，最近文档从标题进入，完整创作结构从“项目”进入。文档状态与可见 Tab 解耦。
- “项目”包含大纲、文件和搜索三个分段；大纲默认以创作结构组织。普通浏览不启用拖拽，排序与移动均通过明确状态或目标选择流程完成。
- 专注输入态由真实可见视口、焦点与安全区共同判断，不使用写死延时。键盘出现时一级导航隐藏，当前输入控件独占底部区域。
- Agent 在手机上使用单会话全屏聊天，会话管理是独立全屏列表。工具、子 Agent 和诊断信息使用可展开消息卡，不占固定辅助栏。
- 普通工作面切换不注入 Agent 上下文。上下文交接条目包含来源、用途、版本、大小和可移除状态，并在进入模型前执行结构化筛选和可配置的高上限。
- Agent 运行由持久运行模型拥有，不依赖当前 React 组件、路由或流式连接。运行必须绑定来源项目、会话和变更审阅边界，并且只由用户明确停止。
- 所有可脱离工作面继续的 Agent、自动化、图像和批量操作统一建模为后台任务。任务至少包含稳定 ID、来源项目、类型、状态、开始时间、最近更新时间和可恢复目标。
- 后台任务状态必须穷尽处理运行中、等待用户、失败、已完成和已停止等状态。只有等待用户与失败计入数字徽标；应用内任务中心是可靠入口。
- 系统通知是默认关闭的用户级偏好，只允许等待用户、失败和用户订阅的完成状态。通知不得包含正文、提示词或工具内容。
- Agent 变更摘要不会自动打开审阅。移动审阅使用按文件的单栏统一 Diff，反馈包含明确来源和大小边界；接受、撤销与继续修改均从审阅工作面发起。
- 故事舞台与导演台是两个独立工作面。故事舞台按故事回合组织为叙事阅读器，导演计划、规则和事件不作为常驻侧栏。
- 玩家提交行动时创建不可变的回合上下文快照。快照记录每个模型输入片段的来源、用途、版本和大小；生成中的回合只消费提交时版本。
- 行动建议只填充自由输入，不直接执行。流式运行期间保留输入草稿但拒绝重复提交。
- 场景图像是可选的回合级正式内容，使用稳定宽高比并支持全屏检查；生成作为可恢复后台任务，不阻塞故事阅读。
- 没有后续依赖的最新回合可通过回合修订更正。存在后续依赖的历史回合只能从目标位置创建新故事分支，原分支保持不变。
- 手机剧情线以分支列表和纵向详情为主，关系图作为次级总览；紧凑宽屏与桌面可以增强为列表加图形视图。
- 当前状态属于故事分支，世界资料属于创作项目。当前状态默认只读，修改必须创建包含来源、时间、分支和基准回合的状态修订并支持撤销或恢复。
- 创作内容使用持续草稿保存，即时偏好自动保存并生效，可执行配置必须完整校验并明确保存，历史事实通过提交、修订或分支写入。不同风险内容不得强行共享同一种保存行为。
- 待同步草稿绑定创作项目与基础版本。本机只允许断线编辑已打开内容；重连后执行版本校验，冲突进入显式审阅。
- 通用控件复用现有 shadcn/ui、Radix、TipTap、Lucide、虚拟列表与 Diff 依赖。旧一级抽屉和边缘手势实现应在新外壳稳定后删除。
- 工作台导航、移动呈现、后台任务、上下文交接、写作、变更审阅与互动故事按各自变化原因划分模块。工作台外壳只组合稳定宿主和导航，不继续吸收功能页面业务。
- 路由与事件状态使用穷尽类型，不通过不断增加布尔 props 表达模式。新的跨模块类型只暴露稳定业务契约。
- 所有用户可见文案必须同时提供中文和英文；错误、空状态、任务状态、通知和确认不可遗漏。
- 黑白纯色外壳、间距、返回和语义状态色在写作与游戏之间共享。游戏表现力来自真实内容和图像，不建立第二套装饰主题。
- 不增加旧布局开关、底栏重排或 Agent 布局选择。可配置项仅保留字体、动效、内容密度、系统通知和场景图像策略等长期偏好，并明确默认值与持久化作用域。

## Testing Decisions

- 测试只断言用户可见行为、持久数据结果和稳定 API 契约，不断言组件内部状态、私有 helper、Tailwind 类名或临时 DOM 结构。
- 自动化测试使用两个高层边界，避免为每个功能建立独立测试入口。
- 第一测试边界是前端应用边界：渲染真实工作台路由、状态仓库、功能组件和国际化，只在 HTTP 边界通过现有 MSW 基础设施提供响应。
- 前端应用边界覆盖：唯一一级高亮、共享菜单不切换模式、模式状态恢复、文档状态恢复、统一返回、专注输入态、显式交接、Agent 后台状态、审阅返回目标、任务恢复和 S/M/L 跨层稳定宿主。
- 现有 WorkbenchShell 响应式测试、ModeRouter 导航保存策略测试、AdaptiveSurface 稳定挂载测试和 WorkspaceMobileLayout 导航测试是前端先例。新用例应逐步迁移到新的应用级工作台边界，旧抽屉与边缘手势用例随实现删除。
- 第二测试边界是后端 API 边界：使用真实 Server、真实应用服务与临时工作区，通过 HTTP 请求验证持久结果和恢复结果。
- 后端 API 边界覆盖：项目隔离、切换保存保护、Agent 运行恢复、后台任务状态、上下文交接元数据、回合上下文快照、故事分支、回合修订、状态修订、冲突检测和可执行配置校验。
- 现有 workspace、interactive、session、document review handler 集成测试及 interactive protocol 集成测试是后端先例，应扩展这些真实边界而不是暴露测试专用生产入口。
- 纯函数单元测试只用于路由状态归约、返回优先级、任务状态转换、上下文大小校验和断线同步决策等边界逻辑。任何单项测试不得运行超过 1 秒。
- 浏览器验收不是第三套内部测试边界，而是交付门槛。必须在真实页面覆盖 320、360、390、430、768、1024 和 1280px，以及横竖屏、中文/英文、亮/暗主题、长文本、空数据、键盘、安全区、断线和后台任务。
- 浏览器验收必须确认页面真实可见、文本无重叠、场景图像正确加载、流式内容布局稳定、粗指针目标可用，并检查 200% 字体、屏幕阅读器语义和减少动效。
- 跨层测试必须验证编辑器、Agent 会话和故事舞台没有重建，草稿、选区、滚动、撤销与输入保持。
- 断线测试必须比较完整同步结果或关键冲突行为，不能只检查一个“离线”文案。
- 故事分支和状态修订测试必须比较完整历史关系与审计结果，不能只断言若干独立字段。
- 前端可见变更必须打开用户已有页面验证；不私自终止或另启用户前端。需要后端更新时使用项目提供的重启流程。

## Out of Scope

- 本规格不重新设计桌面工作台的整体视觉结构。
- 本规格不提供完整离线工作区、离线 Agent 或离线故事生成。
- 本规格不实现用户自定义底栏、旧布局兼容开关或多种 Agent 移动布局。
- 本规格不把所有现有 Book/workspace API 一次性无迁移地强制重命名；迁移必须作为受保护的实现工作完成。
- 本规格不新增自研编辑器、Diff、对话框、虚拟列表、关系图布局或图像查看器。
- 本规格不改变模型或故事生成质量目标，只定义上下文、提交、恢复和呈现边界。
- 本规格不要求每个故事回合都生成场景图像。
- 本规格不把普通提示、保存成功、版本更新或短暂加载塞入任务中心。
- 本规格不在首次启动时请求系统通知权限。
- 本规格不授权发布到上游仓库。

## Further Notes

- 设计依据是已接受的 Mobile Workbench v2 设计规范、领域词汇表和 ADR 0001 至 0029；实现不得静默偏离这些决策。
- 建议按“行为契约 -> 外壳与写作 -> Agent/审阅/任务 -> 游戏 -> 共享管理与断线 -> 删除旧实现”的顺序交付，避免把所有页面同时重写后再集成。
- 这是 Beta 阶段的不兼容重写。发布说明必须明确列出四入口、抽屉与边缘手势移除、移动 Tab 隐藏、Agent 全屏化、模式开关移动、项目术语统一、历史分支与状态修订等变化。
- 实施较大阶段前应评估配置项，但只增加长期用户价值明确且有清晰默认值、作用域和持久化位置的配置。
- 每次提交前更新 CHANGELOG。发布时同步前端版本、CHANGELOG、中文 README、英文 README、Git tag 和包含用户可感知变化与验证说明的 Release notes。
- GitHub Issue 只能发布到 `MeteorAndy/nova`；不得发布到上游。发布时添加 `ready-for-agent`，不添加其他 triage 标签。
